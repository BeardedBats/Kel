# Phase 5.6 — Learning loop (shadow) (implementation record)

Increment: **5.6 — Learning loop (shadow)** per `15_PHASE5_IMPLEMENTATION_SPEC.md` §5.6, with
design docs 11 (§1-6: the five registers, the learnings schema, performance metrics, the curator
pipeline, safety gates, the retro), 13 §4 (metric instrumentation) and 15 §3 (the feature flag).

Status: implemented + engine-verified on `ux/v15-journeys` (commit `ba52869`); audit requested
for `2236881..ba52869`. **No new migration: the increment adds no new storage surface** (doc 11
§7) — learnings are records in the existing memory store, history reuses the existing team
activity stream, and the stats/metrics are derived views. No live caller: every write path
requires an explicit `workforce.learning.shadow` decision and the module is inert otherwise.

## What shipped

- **`kel/learning.py`** (new):
  - **Learnings are memory records** (doc 11 §1-2). `record_learning` writes through the V1.3
    memory store with a workforce `source_type` (`workforce_observed` level 5,
    `workforce_cross_model` level 5, `workforce_inferred` level 6; `user-stated` rides the
    existing `user_confirmation` level 2), so provenance, the trust ladder, append-only
    supersede chains, the user conflict queue, secret scanning and forget semantics all apply
    unchanged. The learning type maps 1:1 onto the memory type (`pattern→convention`,
    `pitfall→limitation`, `preference→preference`, `architecture→component`, `tool→workflow`),
    so the memory (type, topic) identity is exactly the learning (type, key) identity.
  - **Dedup / supersede / decay** (doc 11 §2). Same (key, type): a stronger source supersedes,
    equal trust takes the newest observation, and a weaker source (inference over an
    observation) can never overwrite — the memory ladder decides, and the key never forks.
    Confidence is 1-10; decay is **computed at read time**: observed/inferred/cross-model lose
    one point per 30 days without re-observation (measured from each record's own creation — a
    losing weaker write cannot reset the winner's clock; audit 23, F23-3), user-stated never
    decays; stale learnings leave default retrieval but stay inspectable (`include_stale=True`).
  - **Preference-requires-user** (doc 11 §2). Preferences are recorded only from explicit user
    confirmation (the memory store already refuses anything else); the learning layer refuses
    them without `source='user-stated'` + `confirmed_by='user'`.
  - **Confidence caps + promotion queue** (doc 11 §4). Non-user confidence above the auto cap
    (`AUTO_CONFIDENCE_CAP = 5`) is stored capped and the full request enters the promotion queue
    (`proposal.queued`); user-stated records skip the cap. Nothing promotes automatically.
  - **Correctable** (doc 11 §5). `correct_learning` rides `Memory.correct` — the append-only
    chain is preserved and the corrected record becomes user-stated (the user restated it).
  - **The curator** (doc 11 §4; post-mission, bounded, deterministic). Collects candidates from
    recorded facts — repeat-dismissed lenses (pitfall `lens.<lens>.false-positive`),
    repeat-confirmed lenses (pattern `lens.<lens>.proven`), repeated user corrections
    (`correction.<topic>`, user-stated) and parallel mission conflicts
    (`parallel.undeclared-writes`, `parallel.integration-overlap`) — records them through the
    learning layer (dedup/supersede/caps) and drafts the retro. "Would the system catch this
    next time?" is encoded as the concrete rule behind each candidate.
  - **Retro** (doc 11 §6). `draft_retro` assembles what shipped (task.closed outcomes), what it
    cost (budget reservations of the mission's assignments), what went wrong (live
    blocker/critical findings, close violations, integration conflicts), what was learned (the
    curation's keys) and which proposals were queued — appended as a `retro.drafted` event
    (schema `retro.v1`), skimmable by design.
  - **Shadow staffing proposals** (doc 11 §5). `shadow_proposal` records a proposal with its
    prediction, confidence and basis (state `shadow`). The curator derives exactly one
    deterministic proposal per mission (a clean closed mission → "consider one lower tier…";
    blocker/critical findings → "keep or raise the tier…"): recorded, never applied.
  - **Performance stats** (doc 11 §3). Derived per-lens rates over recorded findings
    (raised/confirmed/dismissed/open, false-positive rate, hit rate), contract/close outcomes,
    budget aggregates and mission conflicts — small samples stay labelled
    ("insufficient (n<3)"), never averaged away.
  - **Validation metrics** (doc 11 §5, doc 13 §4). Gating precision (confirmed / (confirmed +
    dismissed)) and **false-skip**: for each recorded mission tier the deterministic gating plan
    is recomputed and a lens the plan skipped that nonetheless produced live findings is a
    miss — the skip signal that would have caught them earlier. Shadow only; nothing gates.
- **`kel/team.py`** (additive): four new `EVENT_KINDS` (`learning.recorded`, `retro.drafted`,
  `staffing.proposed`, `proposal.queued`) and `Team.record_mission_activity` — one append-only,
  mission-scoped event with the same detail prohibitions as every other activity.
- **`kel/memory.py`** (additive): three workforce `SOURCE_TRUST` entries, documented inline.
- **`kel/assignment.py`** (additive): `flags_snapshot` now carries
  `workforce.learning.shadow` (`KEL_WORKFORCE_LEARNING_SHADOW`, default off; doc 15 §3).
- **Zero behavior change**: with the flag off every automatic write path performs zero writes
  (tested); explicit user corrections are user actions and are never gated (exactly like every
  other memory correction — audit 23, F23-1); no existing module calls the new API; nothing
  applies to staffing, gating or ceremony.

## Deviations / limitations recorded

- The curator's candidate sources are bounded to what the engine records today (findings, user
  corrections, mission conflicts); decisions and stall post-mortems join the rule set when their
  streams record them (documented in the module).
- `performance_stats` is mission-keyed where no project link exists; project scoping is enforced
  for learnings and promotions through the memory store.
- Curator lens evidence is scoped via the optional `missions` argument (the engine records no
  findings->project link); without it the insight text says "the recorded evidence" and this
  limitation stays explicit (audit 23, F23-2).
- Identical-value re-observation appends another live record (the memory store's append-only
  semantics; doc 11 §2 read-time resolution); the view resolves the newest non-superseded per
  (type, key) (audit 23, F23-8).
- Performance rates use recorded findings as the denominator; the doc-11 "dispatched" count is
  not persisted anywhere today (audit 23, F23-9).
- False-skip recomputes the gating plan from the recorded tier (flag-triggered lenses are not
  re-derived from a recorded flag set — the tier is the load-bearing input).
- Increment 21/22 evidence-package nits (R22-3) remain recorded limitations (unchanged).

## Rollback

Flag off (`KEL_WORKFORCE_LEARNING_SHADOW` unset — the default) leaves every stream untouched;
there is no schema to revert; recorded learnings (memories) and events stay inspectable.
